# inventaire.cloud — web application

The web application behind [inventaire.cloud](https://inventaire.cloud), a free and simple inventory tool for professionals and individuals.

It is built **API-first**: the pages are classic server-rendered navigation, but every action goes through one HTTP helper so the same JSON API (`/api/v1`) can serve the web front, the native apps and third-party tools.

## Stack

| Layer      | Choice                                                                                  |
|------------|-----------------------------------------------------------------------------------------|
| Backend    | Laravel 13, PHP 8.4+                                                                    |
| Database   | PostgreSQL, MySQL or MariaDB, never engine-specific SQL (SQLite is not supported)       |
| Front end  | Blade + [Tabler](https://tabler.io) (Bootstrap 5) + Alpine.js (CSP build), bundled by Vite |
| Icons      | [`secondnetwork/blade-tabler-icons`](https://github.com/secondnetwork/blade-tabler-icons) |
| Tests      | Pest (PHP), Vitest + jsdom (JS)                                                         |
| Quality    | Pint, Larastan (level 8), ESLint, Prettier                                              |

Privacy by design: no CDN, no Google Fonts, no external request from the browser. The Inter font and every asset are served by the application itself.

## Requirements

- PHP 8.4 or newer (developed on 8.5; OpenSpout 5.12, which writes the spreadsheets of the exports and reads those of the imports, needs 8.4) with the `pdo_pgsql` and `pdo_mysql` extensions (`pdo_mysql` serves both MySQL and MariaDB) and `intl` (currencies and their decimals, the sorting of names)
- [Composer](https://getcomposer.org) 2
- Node.js 20.19+ / 22.12+ and npm
- [Docker](https://www.docker.com) with Compose, for the development database and mail services

## Development setup

Run every command from this `web/` directory.

1. **Start the services** (PostgreSQL, MySQL, MariaDB, Mailpit) and wait until they are healthy:

   ```bash
   docker compose -f compose.dev.yaml up -d --wait
   ```

   | Service    | Host port                          | Credentials                                  |
   |------------|------------------------------------|----------------------------------------------|
   | PostgreSQL | `54329`                            | database `inventaire`, user `inventaire`, password `secret` |
   | MySQL      | `33069`                            | same as above                                |
   | MariaDB    | `33070`                            | same as above                                |
   | Mailpit    | `1025` (SMTP), `8025` (web UI)     | none                                         |

   Each database also has an `inventaire_test` schema reserved for the test suite. These scripts only run when a volume is first created; use `docker compose -f compose.dev.yaml down -v` to start from scratch.

2. **Install and configure** the application. `composer setup` installs the dependencies, creates `.env` from `.env.example`, generates the application key, builds the assets, then runs `php artisan inventaire:install --from-env`: it checks the services configured in `.env` (database, mail, storage), runs the migrations and marks the instance as installed (see [Installing an instance](#installing-an-instance)):

   ```bash
   composer setup
   ```

   `.env.example` points at the PostgreSQL service. To develop on MySQL or MariaDB instead, uncomment the matching block in `.env` (and comment the PostgreSQL one), then run `php artisan migrate:fresh`.

3. **Run the application.** `composer dev` starts the PHP server, the queue worker, the log tail and the Vite dev server together:

   ```bash
   composer dev
   ```

   The app is then available on <http://localhost:8000> and the mail inbox on <http://localhost:8025>.

4. **Sign in.** There are no passwords (see [Accounts and sign-in](#accounts-and-sign-in)). Open <http://localhost:8000/login>, give the `ADMIN_EMAIL` of `.env` (`admin@example.com` in the example, created as an administrator by `composer setup`) and read the 6-digit code in the mail inbox. `php artisan db:seed` adds a second administrator, `test@example.com`.

## Installing an instance

A new instance is not usable until it is installed. Until then **every web URL redirects to `/install`** (JSON requests get a `503` with `"code": "not_installed"`), and the application runs without a database or a complete `.env`: sessions and cache use files and jobs run inline. The `APP_KEY` is generated on the first web access and written to `.env` (or a static error page explains what to fix when `.env` is not writable). Once the installation is finished, every `/install` URL answers `404`.

There are three ways to install, and they share the same checks:

| Way                              | Use it for                                                              |
|----------------------------------|-------------------------------------------------------------------------|
| The **web wizard** at `/install` | A server you reach with a browser                                       |
| `php artisan inventaire:install` | A terminal: interactive prompts, or options for scripts                 |
| `inventaire:install --from-env`  | Configuration that already exists (Docker variables, `composer setup`)  |

The installer keeps its own files (installed marker, progress, setup token, locks) in `storage/installer/`, readable by the owner and the group so that the web server and the person running the console installer can both use them; `INSTALLER_STATE_PATH` relocates the folder (for example onto a persistent volume). Steps are registered once, in the `App\Installer\InstallStep` enum: the web routes, the wizard and the console installer all iterate over it.

### The setup token (web wizard)

Whoever can open `/install` could point a fresh instance at their own database, so the wizard asks for a one-time **setup token** first. It is created on the first web access, stored in `storage/installer/setup-token` (readable by the owner and the group, so the web server and the person running the console installer can both use it), written to its own log file, `storage/logs/installer.log` (a dedicated channel, so it does not depend on `LOG_CHANNEL`, `LOG_STACK` or `LOG_LEVEL`; readable by the owner and the group only) and printed by:

```bash
php artisan inventaire:install-token
```

The token is compared in constant time, the form accepts 5 attempts per minute and per IP address, the old session is destroyed and a new id issued once it is accepted, and the token is deleted when the installation completes. If the log cannot be written, the page still works and `inventaire:install-token` still prints the token. The console installer does not need it: running it already proves access to the server.

### Behind a reverse proxy

Behind a reverse proxy or a load balancer every request seems to come from the proxy, so the 5-attempts throttle would count all visitors together. Set `TRUSTED_PROXIES` in `.env` (or the environment) to a comma-separated list of the proxies' addresses or CIDR ranges, or `*` for any proxy; it is empty by default (no proxy is believed, so a forged `X-Forwarded-For` header is worthless). The application then reads the real client address from `X-Forwarded-For`.

With an `https://` `APP_URL` the session and CSRF cookies are `Secure` by default: a browser only sends them over HTTPS, so reaching the instance over plain `http` by another way (the container's port 8080 directly, a LAN address) loses the session and signing in never sticks. Set `SESSION_SECURE_COOKIE=false` in `.env` for such a local setup only, never in production.

The public pages of the share links live at `/s/{token}`, with the secret token in the path: they appear in the access logs of the proxy (and of the web server behind it), so treat those logs as sensitive, and keep them off any shared dashboard (see "Share links" under "Inventories").

The application sends `Referrer-Policy: same-origin` with every answer. Leave it as it is: Sanctum recognizes the web front (the requests that get a session) by the `Origin` or `Referer` header, so a proxy that overrides the policy with `no-referrer` makes the front's own same-origin `GET` calls (such as `/api/v1/me`) look like those of a stranger, and the signed-in pages stop working.

It also sends a `Permissions-Policy` header (`app/Http/Middleware/SetPermissionsPolicy.php`): the camera is allowed for the application's own pages only (the barcode scanner), and the features it never uses (microphone, location, motion sensors, USB/serial/HID/Bluetooth/MIDI devices, payments, screen capture) are turned off. A proxy that sets its own policy in its place must keep `camera=(self)`, or the scan from the camera stops working (the scan from a photo still works), and must not forbid `clipboard-write` (the "copy" buttons).

### Trust model

Everything the wizard does is behind the setup token: whoever holds it is trusted like the server administrator. In particular the checks connect to the addresses typed in the forms (database, SMTP, S3 endpoint, Documenso), so they can reach hosts on the internal network, by design: do not hand the token to somebody who should not be able to probe your network. Checks use short timeouts (5 seconds to connect) and never show passwords or API tokens in their messages.

### The steps

The wizard is one page with a progress bar and one AJAX endpoint per step. Each step **tests the real service before saving**, writes its values to `.env` immediately and is recorded in `storage/installer/progress.json`, so an interrupted installation resumes where it stopped (the token is asked again in a new browser session).

1. **Requirements**: the PHP version required by `composer.json`, the extensions (`pdo` with `pdo_pgsql` or `pdo_mysql`, `mbstring`, `openssl`, `tokenizer`, `xml`, `ctype`, `json`, `bcmath`, `fileinfo`, `intl`, `gd` (the only image library used: Imagick does not stand in for it), `zip`, `dom`, `xmlreader` (spreadsheets and PDF of the exports), `curl`; `exif` is recommended, the installer warns without it) and write access to `storage/`, `bootstrap/cache/` and `.env`.
2. **Database**: PostgreSQL 14+, MySQL 8.0+ or MariaDB 10.11+. The connection is tested with a temporary connection; a MariaDB server selected as "MySQL" (or the reverse) is refused, so is a database that holds anything but a previous run of this installer is refused (it must be empty, or have a `migrations` table whose entries are all this application's migrations), and the user must be able to create tables (the check creates, then drops, a table named `installer_probe_check`: it is refused if one already exists, and never touches it). An interrupted installation can be resumed on the same database.
3. **Application**: public URL, default language and display timezone. Dates are always stored in UTC; the display timezone (`APP_TIMEZONE`) is only the zone the server uses when it writes a date itself, such as in the name of a download. Pages show dates in the timezone of the browser.
4. **Email**: SMTP settings and a test address. A 6-digit code is sent there and the step is only validated once it is typed back (valid 15 minutes, 5 attempts; the pending values are kept encrypted in the session).
5. **File storage**: the local disk, or an S3-compatible service (key, secret, region, bucket, endpoint, path-style). The check writes, reads and deletes a temporary file.
6. **Documenso** (optional, can be skipped): instance URL and API token. The check is one authenticated call to the Documenso API, `GET {url}/api/v2/envelope?page=1&perPage=1`, with the bare token in the `Authorization` header ([Documenso API reference](https://docs.documenso.com/docs/developers/api)).
7. **Administrator**: the name and the email address of the first administrator (`ADMIN_NAME` and `ADMIN_EMAIL` in `.env`). Nothing to test here: the account is created by the next step, once the tables exist. There is no password: the administrator signs in with a code sent to this address, so it must be one they can read.
8. **Installation**: runs the migrations, then the post-migration hooks, switches the instance to `APP_ENV=production` / `APP_DEBUG=false` (the web wizard always does, except for values the environment imposes), clears the configuration cache, writes the "installed" marker and deletes the token. The wizard then leads to `/login`.

Anything that has to happen once the tables exist but before the instance is marked installed plugs in as an `App\Installer\PostMigrationHook`, tagged `installer.post-migration`: hooks run after the migrations, must be idempotent (the installation can be run again after a failure) and abort it by throwing an `InstallationException`. The first one is `CreateAdministrator`, which creates the administrator account (or promotes the account that already has the address). Hooks run on the database being installed, whatever the application's default connection points at: in a web request, and in the interactive console installer, the configuration was loaded before the wizard wrote the database settings, so the finalizer makes its temporary connection (`installer_migrate`) the default one while the migrations and the hooks run, then puts everything back. A hook uses `DB` and its models without naming a connection.

### Values provided by the environment

With Docker, configuration usually arrives as real environment variables, which Laravel prefers over `.env`. The installer records the environment the process started with, at the very top of `bootstrap/app.php` (before `.env` is read): every variable in it is **imposed**, even when `.env` holds the same value. The wizard shows imposed values read-only with a "set by the environment" badge, probes them as is, and never writes them. Secrets are never sent back to the browser (an empty box means "unchanged"; to store an empty password on purpose, tick "No password" next to it), and a `.env` that cannot be written is reported with a clear message instead of being silently ignored.

`DB_URL` and `MAIL_URL` are honoured: when one is set (environment or `.env`), the corresponding step treats the connection as provided. Its fields are read-only and masked (a URL usually contains a password), and the checks and the migrations use exactly the configuration the application will use, URL included.

When every setting the installation needs is provided by the environment, nothing has to be written: the wizard does not require `.env` or `bootstrap/cache/` to be writable, which suits read-only containers: when `.env` cannot be written, finalizing such an instance writes nothing but the "installed" marker (set `APP_ENV` and `APP_DEBUG` in the environment too); when it can, the production defaults are written as usual. A `.env` the installer creates is readable by the owner and the group only (`0640`); an existing one keeps its permissions, which the installer never widens.

When `.env` does not exist, the installer creates it from `.env.example`, minus the development defaults: a file created by the installer (on the first web access or by the console command) starts with `APP_ENV=production`, `APP_DEBUG=false`, no database or SMTP credentials, no SMTP host, no sender address and no placeholder administrator, instead of the example's local services. If you copy `.env.example` yourself on a server, set these values yourself. For development, run `composer setup`, which copies the example first and leaves the environment alone.

### From the terminal

```bash
php artisan inventaire:install                 # interactive prompts, pre-filled from .env
php artisan inventaire:install --no-interaction \
    --db-driver=pgsql --db-host=127.0.0.1 --db-port=5432 --db-name=inventaire --db-user=inventaire \
    --app-url=https://inventory.example.com --locale=fr --timezone=Europe/Paris \
    --mail-host=smtp.example.com --mail-port=587 --mail-from-address=hello@example.com --mail-from-name="My Company" \
    --storage=local --admin-name="Jane Doe" --admin-email=jane@example.com
php artisan inventaire:install --from-env      # validate the current configuration and finalize
```

- In interactive mode every value is prompted and the mail step is proven with a code, like in the web wizard.
- In non-interactive mode (`--no-interaction`) the values come from the options (one per wizard field: `php artisan inventaire:install --help`), completed by what `.env` and the environment already provide; the first failing check stops the command with a non-zero exit code. The SMTP server is checked with an authenticated SMTP session, since nobody can read a code. `--skip-mail-test` skips that check (with a warning) and is refused when prompts are possible. Options end up in the shell history and the process list: for passwords, prefer `.env` or the environment.
- Switching to production mode is asked interactively (default yes, except on a `local` instance) and done by default in non-interactive mode; `--keep-environment` leaves `APP_ENV` and `APP_DEBUG` alone. `--db-no-password` and `--mail-no-password` store an empty password on purpose.
- `--from-env` asks nothing, never touches `APP_ENV` or `APP_DEBUG` (the developer path) and writes nothing to `.env` (it does not even need it to be writable): it validates the current configuration with the same live checks, then runs the migrations and finalizes. It is what `composer setup` runs, and what a container entrypoint can run. It needs `ADMIN_NAME` and `ADMIN_EMAIL` among the configuration, like the other required settings.

### Troubleshooting

- *I lost the setup token*: `php artisan inventaire:install-token`.
- *The wizard keeps showing finished steps*: the progress lives in `storage/installer/progress.json`; delete that file to start over (the configuration stays in `.env`).
- *I want to run the wizard again on an installed instance*: delete `storage/installer/installed.json`. This only re-enables the installer; it does not touch the database.

## Accounts and sign-in

Accounts have **no password**: an email address is all it takes. The `/login` page asks for the address, emails a 6-digit code, and typing the code back signs the person in; an address that has no account yet is asked for a name at that moment, so signing in and signing up are the same flow. The same steps are available to API clients as `/api/v1` endpoints:

| Endpoint                      | What it does                                                                                        |
|-------------------------------|-----------------------------------------------------------------------------------------------------|
| `POST /api/v1/auth/code`      | `email`: emails a code. The answer is the same whether the address has an account or not.            |
| `POST /api/v1/auth/verify`    | `email`, `code`, and `name` for a new account: signs in. `201` when the account was created.        |
| `POST /api/v1/auth/logout`    | Ends the session (`204`).                                                                           |
| `GET /api/v1/me`              | The signed-in user (`401` in JSON when nobody is).                                                  |
| `PATCH /api/v1/me`            | `name` and/or `locale`: changes them. A new `locale` also comes back in the `locale` cookie, like the language switcher's. |

The account's other endpoints are in [Workspaces](#workspaces) and [Your account: sessions, data and deletion](#your-account-sessions-data-and-deletion).

Every answer under `/api` is JSON, even for a client that sends no `Accept` header. Refusals of a code are `422` with `errors` and a machine-readable `code`: `login_code_wrong`, `login_code_expired`, `login_code_exhausted`, or `name_required` (right code, unknown address: send it again with `name`, the code is still valid).

- **Codes.** A code is valid for 10 minutes and 5 wrong guesses, and works once. Only a keyed hash (HMAC-SHA256 with `APP_KEY`) is stored, in the `login_codes` table, one row per address: asking again replaces the previous code. The mail is sent right after the response, by Laravel's `defer()` and never through the queue (see [Mails are sent after the response](#mails-are-sent-after-the-response)), in the language of the request, as plain text and simple HTML with nothing fetched from outside.
- **Limits** (`login_codes` in `config/auth.php`; `429` with `Retry-After`). Sending: 3 codes per address and IP address in 10 minutes, 10 per address (from all IP addresses together) in an hour, and 20 per IP address in 10 minutes. Typing codes back: 10 per minute and per IP address and address. An IPv6 client counts as its whole /64, since it can pick any address inside it. Behind a reverse proxy, set `TRUSTED_PROXIES` or every visitor shares one IP address.
- **Wrong codes over time.** Each code tolerates 5 wrong guesses, but asking for a new code does not give back the wrong codes an address already collected: after 10 of them within one period (`failures_per_email`: a fixed hour that opens with the first wrong code, then starts over), **code verification is locked for that address until the period is over**. No code is judged any more for it, **the right one included**, and the answer is `429` with `Retry-After` and `"code": "login_code_locked"`. Anybody who knows an address can lock it that way (that is the price of not letting a 6-digit code be guessed), so an administrator who finds their own address locked can wait for the end of the period or recover as described under "Administrators" below: `php artisan inventaire:make-admin` promotes another address, which signs in as usual. Only a guess that is judged and found wrong counts: the right code, a code that was already burnt or spent, and codes typed for an address that has no pending code cost nothing. The count is kept in the cache (`CACHE_STORE`, `database` by default) and updated with atomic increments, so parallel guesses cannot get around it; a cache store that cannot count (`null`) makes verification fail with a server error instead of silently switching the limit off, and emptying the cache gives the guesses back once.
- **No user enumeration.** Asking for a code does the same work and gives the same answer whether the address has an account or not, and wrong codes are answered the same too. Whether an address has an account is only revealed to somebody who holds a valid code for it. This holds when an administrator closes registration too: see [Closing registration](#closing-registration).
- **Addresses** are stored and looked up in one canonical form: trimmed, lowercase, and the domain in ASCII (punycode: `gmäil.com` becomes `xn--gmil-moa.com`). An accent or a non-Latin letter before the `@` is refused. MySQL's and MariaDB's default collations ignore accents, so without this `john@gmäil.com` would be `john@gmail.com` for them and the owner of a lookalike domain could receive the code of somebody else's account; the migration therefore also gives `users.email` and `login_codes.email` a binary collation (`utf8mb4_bin`) on those engines, so that the database itself compares addresses exactly (PostgreSQL always does). The migration that makes users passwordless brings the addresses already stored to that form, and stops, before changing anything, if two accounts would end up with the same address: merge or delete one of them, then run it again. Rolling it back restores an empty `password` column (the hashes are gone).
- **Staying signed in.** Signing in is remembered for 30 days by the "remember me" cookie (`remember` of the `web` guard in `config/auth.php`). The session itself keeps `SESSION_LIFETIME`, since visitors who are not signed in have sessions too. Signing out ends the session and forgets the cookie of *this* device only: the other devices of the account stay signed in (they share the account's remember token, which signing out leaves alone). To end the other devices' sessions at once, see [Signing out everywhere](#signing-out-everywhere).
- **Language.** `users.locale` is the language of the account. The language of a request is decided before the session starts (see [Translations](#translations)), so the account's language travels in the `locale` cookie: signing in sets the cookie from `users.locale` (an account without one takes the language in use), and the language switcher updates the cookie and `users.locale` together.
- **Stateful requests (Sanctum).** The web front calls the API with its session cookie and CSRF token. Laravel Sanctum treats a request as coming from the front when its `Referer` or `Origin` host is listed in `SANCTUM_STATEFUL_DOMAINS`; by default that is the usual development hosts and the host (with the port) of `APP_URL`, so an instance works when it is reached on its public address. If it is also reached on another host (a second domain, a LAN address, another port), signing in from there answers `403` with `"code": "not_stateful"`: list every such host, with its port when it is not the default one, in `.env`:

  ```dotenv
  SANCTUM_STATEFUL_DOMAINS=inventory.example.com,inventory.example.net:8443
  ```

  The variable replaces the default list, so repeat the host of `APP_URL` in it. The sign-in endpoints refuse any other caller on purpose: the session and the CSRF check are what keep a forged form on another site from signing a visitor into somebody else's account.
- **Administrators.** `users.is_admin` marks the people who administer the instance. The installer creates the first one; to add one later, or to recover when nobody can sign in as one (an address locked by too many wrong codes included: see above), run `php artisan inventaire:make-admin jane@example.com --name="Jane Doe"` (with Docker: `docker compose exec app php artisan inventaire:make-admin ...`). It creates the account or promotes the existing one (keeping its name), and can be run again safely. Administrators also manage accounts from the interface: see [Administration](#administration).

## Workspaces

Inventories live in workspaces. Every account belongs to at least one, in which it holds a role, and works in one at a time (its *current* workspace).

- **Tables.** `workspaces` (`id` for the database, a unique `ulid` for the outside world: URLs, API, never the numeric key), `workspace_user` (the membership: `role`, one row per user and workspace, deleted with either side) and `users.current_workspace_id` (forgotten if that workspace is deleted).
- **Roles** (`App\Workspaces\WorkspaceRole`): `owner`, `editor`, `viewer`. The abilities are asked through `canView()`, `canEdit()` (content, from lot 4 on) and `canManage()` (the workspace itself: rename, delete, members), never by comparing roles. `App\Policies\WorkspacePolicy` maps them to actions: any member can see a workspace, only owners change, delete or manage it. Somebody who does not belong to a workspace is answered `404`, as if it did not exist; a member without the right gets `403`, with a message that names what was refused. The `role` column is a free string, so a row may hold a word this version does not know (a rollback, an edit by hand): `App\Workspaces\StoredRole` reads it as `viewer`, the role with the fewest rights, and logs a warning once per value and process, instead of failing the pages that list workspaces.
- **A personal workspace for everyone.** An account always has one: it is created, named "Personal space" in the language of the account, in the transaction that creates the account (`Accounts::register()`: sign-up, the installer's administrator, `inventaire:make-admin`), when an existing account without any is promoted to administrator, and at sign-in for an account that lost its last one. The migration `give_every_user_a_workspace` gives one to every account that existed before workspaces did; it can be run again safely.
- **The current workspace** is `users.current_workspace_id`; when it is empty, or no longer a workspace the user belongs to, it is the first one they joined. Creating a workspace makes it current. Deleting the current one moves the user to another. `Workspaces::current()` heals an account that belongs to none (the rules prevent it, but a row changed by hand or a restore can break them): it gives it its personal workspace, so that nobody is ever stuck without somewhere to work.
- **The last workspace** of an account cannot be deleted (`409`, `"code": "last_workspace"`). Deleting a workspace that other people belong to gives a personal workspace to those who had no other one.
- **Limits.** An account cannot belong to more than `workspaces.max_per_user` workspaces (50; `WORKSPACES_MAX_PER_USER`): beyond it, creating one is a `409` with `"code": "workspace_limit_reached"` and the `limit`. Accepting an invitation counts against the same limit (`409`, `"code": "membership_limit_reached"`). Creating is also throttled per user to `workspaces.create_per_hour` (20 an hour; `WORKSPACES_CREATE_PER_HOUR`), then `429`. Both are in `config/workspaces.php`.
- **Members and invitations** (`App\Workspaces\Members`, `App\Workspaces\Invitations`). A workspace has one owner, and only the owner decides who belongs to it: invite (as an editor or a viewer), withdraw or send an invitation again, change a role, remove a member, hand the ownership over (the old owner becomes an editor; that one is for a person at their browser, `POST /api/v1/workspaces/{workspace}/transfer` refuses an API token). The owner never leaves, is never removed nor demoted. A member can leave; an account left without any workspace is given a personal one. An invitation is bound to an **email address**, not to a secret link: the invitee signs in with that address (the mailed code proves it is theirs), sees the invitation among theirs and accepts or declines it; the mail only links to `/app/invitations`. It lapses after `workspaces.invitation_ttl_days` (14; `WORKSPACES_INVITATION_TTL_DAYS`), is invisible once it has (`inventaire:prune-invitations` clears the table every hour), and can be sent again at most every 10 minutes. A workspace holds at most `workspaces.max_members` members and waiting invitations together (50; `WORKSPACES_MAX_MEMBERS`); accepting an invitation counts against the same limit as creating a workspace, `workspaces.max_per_user` (50; see **Limits** above); sending mails is throttled per owner to `workspaces.invitations_per_hour` (20; `WORKSPACES_INVITATIONS_PER_HOUR`) and per address to `workspaces.invitations_per_address_per_day` (5, from everybody on the instance together; `WORKSPACES_INVITATIONS_PER_ADDRESS_PER_DAY`), then `429`. A member is named in the API by `users.ulid`, a random lowercase ULID-shaped value drawn when the account is made (no creation date in it), never by the number of the account. **While registration is closed**, a waiting invitation is the ticket of its address (see [Closing registration](#closing-registration)).
- **Concurrency.** Whatever removes memberships or workspaces runs in one transaction under row locks taken in a global order, which everything that adds or changes members follows too: see `App\Workspaces\Locks`. A transaction the database picks as the loser of a deadlock is retried (`App\Database\DeadlockRetries`).

| Endpoint                            | What it does                                                                                  |
|-------------------------------------|-----------------------------------------------------------------------------------------------|
| `GET /api/v1/workspaces`            | Your workspaces, oldest membership first: `id` (the ULID), `name`, `role`, `is_current`, `created_at`. |
| `POST /api/v1/workspaces`           | `name` (required, trimmed, at most 100 characters): creates a workspace you own and work in (`201`). |
| `PATCH /api/v1/workspaces/{id}`     | `name`: renames it (owners only).                                                              |
| `DELETE /api/v1/workspaces/{id}`    | Deletes it, and everything in it (owners only; `204`).                                         |
| `PUT /api/v1/me/current-workspace`  | `workspace` (a ULID): the workspace to work in. One you do not belong to is refused like one that does not exist (`422`). |

Answers are in the `data` envelope. Errors have a `message` in the language of the request and, for conflicts, a machine-readable `code`.

In the interface, the header has a switcher (before the account menu) and `/app/workspaces` lists the workspaces to create, rename in place, delete (with a confirmation in the row) and choose between. The switcher and the page share one Alpine store, so a change shows in the header without a reload.

## Inventories

An inventory is a table of items that share the same typed fields, kept in a workspace. Its **fields** say what an item can hold, its **items** hold it; both go with the inventory when it is deleted, and an inventory goes with its workspace (foreign keys cascade, and the models' own `delete()` is what the application calls).

- **Tables.** `inventories` (`workspace_id`, `name` 120, `description`), `inventory_fields` (`inventory_id`, `name` 120, `type`, `options` JSON, `required`, `position`) and `items` (`inventory_id`, `values` JSON, `created_by`, `updated_by`: forgotten, not deleted, with the account). Each has a unique `ulid` for the outside world (URLs, API) and keeps its numeric key to itself; ULIDs are looked up whatever their case, also as the child of another binding (`App\Models\Concerns\HasUlidRouteKey`).
- **Values.** `items.values` is one JSON object keyed by the ULID of the field, always written as an object (`{}` when empty: `App\Models\Casts\JsonObject`). An empty value (null, an empty text, an empty list) is never stored: the key is removed. Numbers are stored as decimal **strings** (`"12.50"`), never as JSON numbers, which MySQL and MariaDB would turn into floating point values. What is read back goes through the type again (`present()`), and only for the fields that exist, in their order: a stray key left in a row is never given out.
- **Roles** (`App\Policies\InventoryPolicy`; the abilities are mapped from `WorkspaceRole` in `InventoryPolicy::abilities()`, which the API also gives as `abilities`): every member reads; owners and editors add and change inventories, their fields and their items; only owners delete an inventory. A non-member gets `404`, like a workspace; a member without the right `403`. A row that does not exist and a row you may not see are answered alike (the framework's `ModelNotFoundException` is rendered as a plain `404`: its own message would name the model and the key).
- **Quotas** (`config/inventories.php`): `max_per_workspace` inventories per workspace (100; `INVENTORIES_MAX_PER_WORKSPACE`, counted under the lock of the workspace's row), `max_fields` fields (100; `INVENTORIES_MAX_FIELDS`) and `max_items` items (10000; `INVENTORIES_MAX_ITEMS`) per inventory, counted under the lock of the inventory's row. Beyond one, the API answers `409` with `"code": "inventory_limit_reached"`, `field_limit_reached` or `item_limit_reached`, and the `limit`.
- **History and files.** Every creation and change of values of an item writes a revision (`item_revisions`: who, when, the stored values before and after; none when nothing changes; `INVENTORIES_MAX_REVISIONS_PER_ITEM`, 100, the oldest go first), read through `GET /api/v1/inventories/{inventory}/items/{item}/revisions` (each line has a ULID `id`, and its author is given by `name` only, never by number). Deleting a field takes its values out of the history of the inventory in the same transaction (a revision left with nothing is deleted). Files are attached under `.../items/{item}/attachments` (a plain attachment, or the content of a `file` or `photo` field with `field=<ULID>`): the type is detected from the content, never from what the client says; the name is cleaned up and never part of a path (`workspaces/{workspace}/inventories/{inventory}/items/{item}/{attachment}`, ULIDs all); downloads are `attachment` with `nosniff` and a sandbox CSP, shown in the page (`?inline=1`) only for JPEG, PNG, WebP, GIF and PDF (a PDF shown in the page gets `default-src 'none'` without `sandbox`, which Chromium needs to draw it). A file is revalidated at each read (`ETag` made of its ULID, `304` for a reader who has it), a thumbnail is kept for an hour; a file missing from its disk, or on a disk no longer configured, is a `404`, a disk that cannot be read a `503` (logged). Limits (`config/inventories.php`): `INVENTORIES_MAX_ATTACHMENT_SIZE_MB` (20), `INVENTORIES_MAX_ATTACHMENTS_PER_ITEM` (20, the files of fields included) `INVENTORIES_STORAGE_PER_WORKSPACE_MB` (1024, a counter on the workspace kept under its lock; `inventaire:upgrade` adds the sizes up again) and `INVENTORIES_UPLOADS_PER_MINUTE` (30 per person, `429` beyond). The disk is `ATTACHMENTS_DISK` (the default disk when empty; a private disk, `public` is refused). Images get a JPEG thumbnail made by GD (480 px, EXIF orientation applied, no metadata; the `exif` PHP extension is in the Docker image); an image of an allowed type that GD cannot decode (an animated WebP) is kept without one, in a photo field too. Deleting a file, an item, a file field, an inventory, a workspace or an account deletes its files from the disk after the commit, in a queued job (`PurgeStoredFiles`): keep a queue worker running. The history and the files hang from their inventory (`inventory_id` cascades) and not from the item and the field, whose deletion removes them in the application: MySQL 9.7 does not carry a cascade through four tables for the second inventory onwards.
- **Exports.** A member of a workspace (a viewer too) takes the items of an inventory out as a file: `POST /api/v1/inventories/{inventory}/exports` with `format` (`xlsx`, `ods`, `csv`, `json`, `pdf` or `zip`), `scope` (`all`, the default, or `view`, with the `query` of the grid: `q`, `sort`, `direction`, `filter`, as the list of items takes them), `delimiter` (`comma`, `semicolon` or `tab`, for a CSV: the semicolon in French, the comma otherwise) and `files` (`photos` or `all`, for a zip). It answers `202` with the export (`pending`) and a queued job (`GenerateExport`, tried once, 15 minutes at most: keep a queue worker running, and `retry_after` of the queue above that, `DB_QUEUE_RETRY_AFTER`, 960) writes the file next to the other private files, under the folder of its inventory (`workspaces/{workspace}/inventories/{inventory}/exports/{export}/`). `GET .../exports` lists the person's exports that did not expire (20 at most), `GET .../exports/{export}` reads one (`status`: `pending`, `running`, `completed`, `failed`; `error`, the message of a failure; `download_url`, a path of the application, once ready), `GET .../exports/{export}/download` downloads it (`attachment`, `nosniff`, `no-store`; `409 export_not_ready` before) and `DELETE` deletes it with its file. An export is its author's alone: another person's is a `404`. Limits (`config/inventories.php`): `INVENTORIES_MAX_ACTIVE_EXPORTS` (10 not expired exports per person, any state, counted under the lock of their row: `409 export_limit_reached`), `INVENTORIES_EXPORTS_PER_MINUTE` (10, `429`), `INVENTORIES_EXPORT_TTL_HOURS` (24), `INVENTORIES_PDF_MAX_ITEMS` (500 items of up to 8 fields, fewer in proportion beyond: dompdf lays the whole document out in memory, about 30 KB a value; `422` on `format` beyond) and `INVENTORIES_EXPORT_STALE_MINUTES` (60). A zip with no file in the scope is a `422` on `format`. `php artisan inventaire:prune-exports`, scheduled every hour (the `scheduler` of the Docker example runs it; elsewhere, `php artisan schedule:run` every minute from cron), deletes the exports that expired with their files, gives up on the ones whose worker was lost and clears scratch files; the files are also purged with the inventory, the workspace and the account. Spreadsheets are written with OpenSpout, typed cells and never a formula (a text that starts with `=` is a text; the CSV puts a quote in front of it), PDFs with dompdf (DejaVu Sans, its fonts cache under `storage/framework/dompdf`), the zip with `ZipArchive`; the JSON is `{"format": "inventaire.cloud/export", "version": 1, "inventory", "fields", "items"}` with the values as the API gives them.
- **Imports.** An editor or an owner (not a viewer) brings the rows of a spreadsheet into an inventory: `POST /api/v1/inventories/{inventory}/imports` with a multipart `file` (XLSX, ODS, CSV, TSV or TXT; at most `INVENTORIES_IMPORT_MAX_SIZE_MB`, 10) and, when the person already knows, `has_header` (true by default), `delimiter` (`comma`, `semicolon` or `tab`) and `encoding` (`utf-8`, `windows-1252` or `utf-16`). The file is read at once, in the request (the header is the first row of the file and nothing else: when it is empty the columns are `Column A`, `Column B`... and the data start on the second row; a row further down with a value past the last column shown is a row in error): a spreadsheet's active sheet (else its first visible one), or a text file whose encoding is detected (UTF-16 with its byte order mark, UTF-8 when the whole file is valid, else Windows-1252) and whose separator is the one of `; , tab` that splits the first lines the same way outside quotes; the byte order mark and the apostrophe an export puts before a text a spreadsheet would run as a formula (`=`, `+`, `-`, `@`) are taken off. The answer (`201`, the import `uploaded`) gives the `columns` (`index`, `header`, three `samples`, the type `guess`ed from the first 50 rows: yes/no, date, date and time, time, number, amount, percentage, email, URL, long text, text; and `fraction_like`, true when the values are all numbers between -1 and 1 without a percent sign or a currency and not all whole, as the cells a spreadsheet shows as percentages are: 12.5 % is stored as 0.125. They are imported as they are, never multiplied by a hundred, and the front warns before such a column goes to a percentage field), the `options` it will read the cells with (`decimal` and `date_order` are found in the values when they show them, else follow the language and the separator) and a `mapping` proposal: the field with the same name (case, accents and a unit in brackets ignored), `ignore` for the columns an export adds (identifier, created, modified), else a new field of the type guessed (`ignore` for someone who may not create fields). `PATCH .../imports/{import}` reads the file again with other `has_header`, `delimiter`, `encoding` (and keeps `decimal`, `date_order`, `on_error`); `POST .../imports/{import}/start` takes the `mapping` (a list of `{column, target: ignore|field|new, field, type, name}`) and the options, checks it (`422` on `mapping` with a `code`: `unknown_column`, `duplicate_column`, `unknown_field`, `field_not_importable`, `duplicate_field`, `invalid_field_type`, `invalid_field_name`, `duplicate_field_name`, `field_name_taken`, `cannot_manage_fields`, `required_field_unmapped`, `nothing_mapped`; `409 field_limit_reached`) and queues the job (`ImportItems`, on the queue of the exports, tried once, 15 minutes at most: the same worker and the same `retry_after` as the exports). It answers `202`. The job reads every cell by the type of its field (numbers `1 234,56`, `1,234.56`, `12 €`, `12 %`, dates `2026-03-15` and `15/03/2026` or `03/15/2026`, yes/no `oui`, `x`, choices by label...; a moment without an offset is read in the time zone of the application, and one in the hour the clocks skip when they go forward is refused, one in the hour they show twice is the first of the two; a choice is found by its label as written, then without its accents, and a label that holds a comma is recognised in a list of choices, whereas a tag that holds a comma is cut in two, tags being cut at the commas, semicolons and line breaks), checks the values as an item's are, creates the new fields (the options of a number, an amount, a text, a rating and the choices of a choice field are drawn from the values) and the items in **one transaction** under the lock of the inventory (`Items::createMany`: the quota of items, the counter moved once, the history written in bulk), then records the report: `rows_total`, `rows_imported`, `rows_failed`, `fields_created` and the first 100 `errors` (`row`, `column`, `message`). With `on_error` `abort` (the default) one row in error fails the whole import (`invalid_rows`) and nothing is written; with `skip` the rows in error are left out and reported. The source file is deleted when the job ends, whatever the result. `GET .../imports` lists the person's imports that did not expire (20 at most), `GET .../imports/{import}` reads one (`status`: `uploaded`, `pending`, `running`, `completed`, `failed`; `error`, the message of a failure), `DELETE` cancels one with its file (`409 import_running` while the job works on it). An import is its author's alone: another person's is a `404`. Limits (`config/inventories.php`): `INVENTORIES_MAX_ACTIVE_IMPORTS` (3 unfinished imports per person and inventory: `409 import_limit_reached`), `INVENTORIES_IMPORTS_PER_MINUTE` (10 files sent or read again, `429`), `INVENTORIES_IMPORT_MAX_ROWS` (10 000 rows, empty ones not counted: `too_many_rows`; a file with more than 1 100 000 lines, empty ones included, is refused with `too_many_lines` (when the lines are past the first rows that the upload looks at, the import itself fails with that code, and `too_many_columns` for a row that is too wide): a spreadsheet often ends with a million empty rows, which are read to the end all the same), `INVENTORIES_IMPORT_MAX_COLUMNS` (200: the columns that hold something; a row that the file would have the library build wider than the larger of this and 1 024 cells (512 for an Excel sheet, whose rows take time as the square of their width), the width that older versions of LibreOffice pad their rows to, is refused before it is built with `too_many_columns`: a cell repeated fifty million times, a sheet announcing `ZZZZZZ`, ten megabytes of separators, and a row of 16 384 cells, which takes seconds to build; the 16 384 columns of Excel and recent versions are not built, as the padding cell is left out; and a sheet that would be built with more than twice the rows by the columns an import takes, 4 000 000 with the defaults, the empty cells of its formatting and the repeated rows counted, is refused with `too_many_cells`; the analysis of the file looks at its first 1 000 lines), `INVENTORIES_IMPORT_MAX_UNPACKED_SIZE_MB` (100: a spreadsheet is a zip archive; the sizes it announces are summed first, then its parts are unpacked into nothing and the bytes that really come out are counted, since the announced sizes can be forged), `INVENTORIES_IMPORT_TTL_HOURS` (24: a file sent and not started, and the report of a finished import) and `INVENTORIES_IMPORT_STALE_MINUTES` (60). `php artisan inventaire:prune-imports`, scheduled every hour with `inventaire:prune-exports`, deletes the imports that expired with their files, gives up on the ones whose worker was lost and clears scratch files; the files are also purged with the inventory, the workspace and the account. Dates and times without an offset are read in the time zone of the application (`APP_TIMEZONE`); the update of existing items through the identifier column is not done (the identifier column is ignored).
- **Share links** (`App\Inventories\Sharing\ShareLinks`, `share_links`). The owner of the workspace (`InventoryPolicy::share`, the `share` ability of the inventory) shares an inventory read-only through a secret address, `/s/{token}`: `GET`, `POST` and `DELETE /api/v1/inventories/{inventory}/share-links[/{shareLink}]` (all `manage`, the list included, since it holds the addresses; editors and viewers get `403`, strangers `404`). `POST` takes `label` (80 characters, one line), `include_files` (true by default: whether files and photos are shown) and `expires_in_days` (7, 30, 90 or 365; 30 when left out, JSON `null` for a link that never expires) and answers `201` with the link and its `url`, built from `APP_URL`, `Cache-Control: no-store`. The token is 32 random bytes (base64url, 43 characters); the table keeps its SHA-256 (`token_hash`, unique, the only way a visitor's link is looked up) and the token encrypted with the application key (`token_encrypted`), so the owner can copy the address again. **Rotating `APP_KEY`** without keeping the old key in `APP_PREVIOUS_KEYS` (comma-separated list, see `config/app.php`) makes every stored token unreadable: `url` becomes `null` in the API and the page says so, the links keep opening by their hash for whoever holds the address, and the owners revoke them and make new ones. **A link belongs to the inventory, not to its author**: it keeps working when its author leaves the workspace, is no longer an owner or deletes their account (`created_by_id` becomes `null`), so whoever holds the URL reads the inventory until it expires or an owner revokes it. The API says whether the author is still an owner (`created_by.is_owner`, `created_by` is `null` once the account is gone) and the sharing page marks the other links "Created by a former member". **Access logs**: the token is in the path, so `/s/{token}` shows up in the access logs of the reverse proxy and of the web server; keep those logs private and short-lived, and revoke a link whose address leaked. Limits (`config/inventories.php`): `INVENTORIES_MAX_SHARE_LINKS` (20 per inventory, counting the links that still work only: the expired ones, which wait to be deleted, do not count; `409 share_link_limit_reached`, counted under the lock of the inventory), `INVENTORIES_SHARE_LINK_CREATIONS_PER_HOUR` (20 per person, `429`), and, for the public page and the files it serves, `INVENTORIES_SHARE_PAGE_PER_MINUTE` (120) and `INVENTORIES_SHARE_FILES_PER_MINUTE` (600). An administrator can turn sharing off (`share_links_enabled` in the settings, on by default): creation is then refused with `409 share_links_disabled` and every link answers as if it did not exist (nothing is deleted). Unknown, malformed, expired, revoked and disabled links are indistinguishable. `last_used_at` moves at most once an hour (one conditional `UPDATE`). `php artisan inventaire:prune-share-links`, scheduled daily, deletes the links that expired more than 30 days ago. The links hang from their inventory (`inventory_id` cascades). **The public page** (`/s/{token}`, `SharePageController`, `SharedInventory`) is drawn by the server with no script: the name and description of the inventory, its fields as columns and its items 50 a page (`?page=`), searched by words (`?q=`, 100 characters at most), with the values written as the exports write them (language of the browser, timezone of the instance) plus links for web addresses (`http:`/`https:` only), emails and phone numbers, badges, stars and swatches. It never shows the workspace, its members, who made an item or uploaded a file, the history or the versions. The photos and files are served by `/s/{token}/items/{item}/attachments/{attachment}` and `.../thumbnail` (only those of a photo or file field, and only when the link has `include_files`), judged against the link at each request and never cached beyond a revalidation (`private, no-cache`). These routes keep no session, no cookie and no CSRF check (a session would store the address): the answer carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: private, no-store`, and the pace is counted per network and link (`share-page`, `share-files` limiters; keys hold the SHA-256 of the token, never the token, with a coarser per-network count of ten times the limit as a net for made-up addresses). The owners reach their links from the **Share** button of the inventory page (`/app/w/{workspace}/inventories/{inventory}/sharing`, a 403 for editors and viewers), and the administrator's switch is on `/app/admin/settings`.
- **Concurrency.** Every write to an inventory (its name, its fields, its items) locks the inventory first, then reads its fields with a plain read while it holds the lock (`App\Workspaces\Locks`, which documents the global order: ... workspaces, memberships, inventories, items; the fields have no row locks of their own, because a locking read on them would also lock the gap where the first field of the next inventory goes, on MySQL and MariaDB, and make unrelated inventories wait for each other), in one transaction retried on a deadlock. That is what makes a quota exact, a field name unique (no portable unique index folds capitals and accents, so it is checked in PHP under the lock), a field deletion leave no orphan value in an item written at the same moment, and two updates of one item merge instead of overwriting each other.
- **Fields.** Names (of fields, inventories and choices) are kept in Unicode normalization form C, so an accented letter written as one character or as a letter plus a combining accent is the same text. Field names are unique per inventory: the case is not counted (`Straße` is `STRASSE`) and neither is the way an accent is written, but **accents do count** (`Prénom` is not `Prenom`). A new field goes at the end; `PUT .../fields/order` takes the ULIDs of *all* the fields, each once, or answers `422`. The **type cannot change** once the field exists (`422` on `type`). Options sent in an update are merged over the ones the field has (an option sent as `null` goes back to its default) and judged together by the type; an option the type does not have is a `422` on `options.<name>`. Changing options takes from the items only what can no longer mean anything, in the same transaction and through the query builder (`updated_at` untouched): the ids of **choices deleted** from a select or a multiple choice, and the **ratings above a lowered maximum**, are removed from every item. Any other change (decimals, minimum, maximum or unit of a number, currency, length of a text, format of a barcode, labels and colors of choices, new choices...) leaves the stored values exactly as they are: they were valid when written and are not judged again until somebody changes them. **Deleting a field** removes its key from every item of the inventory in the same transaction, by chunks, through the query builder (the items keep their `updated_at`).
- **Items.** `values` is keyed by the ULID of the field (in any case, as in a URL) and validated against the fields as they are under the lock: a key that is no field of the inventory is a `422` on `values.<key>` (never ignored); a required field must have a value when the item is created and cannot be cleared when its key is sent (an update that does not mention it leaves it alone, whatever the item holds); an update only changes the keys it sends, an empty value clears; an update that changes nothing writes nothing. Messages name the field by its name. The list is 50 a page, newest first (`data`, `links`, `meta`).

**Field types** (one class each in `app/Inventories/Fields/`, behind the `FieldType` contract and the `FieldTypes` registry; `GET /api/v1/field-types` lists them with their label). Every write goes `prepare` (trim) → empty? (clears) → rules → `normalize` (what is stored):

| `type`        | Options (defaults)                                                                                   | A value, and what is stored                                                                                   |
|---------------|------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|
| `text`        | `max_length` 1..1000 (255)                                                                           | One line, no control character (`App\Rules\SingleLineText`), trimmed.                                         |
| `textarea`    |                                                                                                      | Up to 10000 characters; line breaks (stored as `\n`) and tabs allowed, other control characters refused.      |
| `number`      | `decimals` 0..6 (0), `min`, `max`, `unit` (16)                                                       | A JSON number or a string with a dot, below 1e15; **more decimals than allowed is a `422`**, never rounded (a float in exponent notation, `1.0e-5`, is shifted to plain digits exactly; one too far from zero to be read exactly must be sent as text); stored `"12.50"`. |
| `money`       | `currency`: ISO 4217 code of a currency **in use somewhere today** (`EUR`; from ICU's currency map: no peseta, no franc, no funds code or metal); a field keeps the currency it has | As a number, with the decimals of the currency (ICU: 2 euro, 0 yen, 3 dinar). ICU is asked **once**, when the field is created and when its currency changes: the decimals are then kept in the options of the field (`{"currency": "EUR", "decimals": 2}`; read-only, `decimals` cannot be sent), so a later update of the ICU data cannot make stored amounts fail.                                 |
| `percentage`  | `decimals` 0..4 (2)                                                                                  | As a number: `"12.50"` is 12.5 %.                                                                             |

| `date`        |                                                                                                      | `YYYY-MM-DD`, years 1000..9999.                                                                               |
| `datetime`    |                                                                                                      | ISO 8601 **with its offset**, stored in UTC to the second (`2026-10-15T12:30:00Z`); a fraction of a second is refused (`Date.toISOString()` writes one), nothing is dropped silently. |
| `time`        |                                                                                                      | `HH:MM`.                                                                                                      |
| `select`      | `choices`: 1..200 of `{id, label (100), color}`; `color` is one of `gray red orange yellow green teal blue indigo purple pink` | The id of a choice.                                                                          |
| `multiselect` | the same                                                                                             | A list of ids, each once.                                                                                     |
| `tags`        |                                                                                                      | Up to 30 lines of 1..50 characters; trimmed, repeats (capitals ignored) dropped.                              |
| `url`         |                                                                                                      | `http` or `https`, at most 2048 characters.                                                                   |
| `email`       |                                                                                                      | At most 254 characters, kept as written.                                                                      |
| `phone`       |                                                                                                      | At most 32 characters: optional leading `+`, digits, spaces and `().-`, at least 3 digits.                    |
| `rating`      | `max` 3..10 (5)                                                                                      | A whole number from 1 to `max`, stored as a JSON **integer** (the one exception to decimal strings: a small whole number has no precision to lose). |
| `color`       |                                                                                                      | `#rrggbb`, stored in lowercase.                                                                               |
| `barcode`     | `format`: `any`, `ean13`, `ean8`, `upca`, `isbn10`, `isbn13` (`any`)                                 | The check digit is verified (ISBNs may be written with hyphens; stored as digits); `any`: 1..64 of letters, digits, `-` `.`. |

The **choices** of a `select` or `multiselect` have ids made by the server (8 random characters, `a-z0-9`) when a choice is sent without one, and kept when the choice already exists. An id the field never had is **not** taken from the client: that choice gets a new one, so a deleted choice cannot come back with its old id and bring old values with it. Values hold ids, never labels, so a choice can be renamed freely; a value whose choice was deleted is dropped when read (the items are not rewritten).

Answers are in the `data` envelope; ids are ULIDs and dates ISO 8601. Item, field and inventory ULIDs that belong to another inventory (or workspace) are a `404`, never a `403`.

**Scanning barcodes** (front only: no schema or API change). Every `barcode` field of the item form has a scan button, and so has the search box of the list. A scan reads the code with the camera, or from a photo (a file chooser that offers the camera app and the gallery of a phone: it is also the way when the camera is refused or missing; a photo of more than 2000 px on its longest side is shrunk before it is read). The camera stops when the page goes to the background (the panel then offers to restart it), and a read that cannot be the code of the field (the barcode of a bottle in an ISBN field) is ignored, with a message. The browser only gives the camera to a secure page, so camera access needs the instance to be served over HTTPS (`localhost` works for development), and a `Permissions-Policy` header set by a proxy must keep `camera=(self)` (see "Behind a reverse proxy"). The reader is `barcode-detector` used as a ponyfill (the same code on every browser, Safari and Firefox included) on top of ZXing compiled to WebAssembly; it is self-hosted, never fetched from a CDN: Vite emits the `.wasm` file (about 1 MB) under `/build/assets/`, and it is loaded with the reader's own chunk at the first scan only. The format of the field steers what is looked for (`resources/js/scanner/formats.js`): a UPC-A field gets its 12 digits, an ISBN-10 field the ISBN-10 rebuilt from the EAN-13 of the book. The code then goes through the same path as a typed one, and the server stays the only judge of it. A code read in the search box is searched at once (a UPC-A as its 12 digits and the EAN-13 of a book as the 9 digits it shares with its ISBN-10, so that either form an item holds is found), and when no item has it the empty state offers to add an item with that code.

If you add a `Content-Security-Policy` in front of the application, the scan needs: `'wasm-unsafe-eval'` in `script-src` (the reader is WebAssembly, which a policy refuses to compile without it, and `'unsafe-eval'` is not needed), `'self'` in `connect-src` (the `.wasm` file is fetched from `/build/assets/`), and `blob:` in `img-src` (a photo goes through an object URL to be shrunk, and the reader uses one when the browser cannot decode a photo itself). The reader starts no worker and loads no script from a `blob:` URL; the picture of the camera is a stream, which `media-src` does not govern.

## The public API

Everything the web application does with your data goes through the JSON API under `/api/v1`, and scripts, integrations and apps can use it too, with a **personal access token**.

- **Tokens.** The account page has an "API tokens" card: a name, one to three abilities and an expiry (7, 30, 90 days, a year, or never). The value starts with `inv_` (`SANCTUM_TOKEN_PREFIX`) and is shown **once**, when the token is made. `GET`, `POST` and `DELETE /api/v1/me/tokens` are behind the web session only (a token cannot make others, nor revoke itself). A person may have `MAX_API_TOKENS` live tokens (20; more is a `409` `token_limit_reached`) and make ten an hour. Signing out everywhere revokes them all. Expired tokens are refused at once and deleted a day later by `sanctum:prune-expired`, which the scheduler runs daily (`routes/console.php`; the `scheduler` service of `docker/compose.yaml`, or `php artisan schedule:run` every minute from cron).
- **Using one.** `Authorization: Bearer inv_…` on any `/api/v1` request, for example `curl -H "Authorization: Bearer inv_…" https://your.instance/api/v1/workspaces`. A token that is missing, malformed, expired or revoked is a `401`.
- **Abilities.** `read` is every `GET`; `write` is the content of an inventory (items, attachments, exports, imports); `manage` is the structure (workspaces, inventories, fields), the people of a workspace and the share links of an inventory. They are independent (`write` and `manage` do not include `read`, and a token that cannot read can hardly be used: the identifiers are found with `GET`; what `write` answers is the resource it wrote; `manage` can delete a workspace or an inventory with all its data). Creating a field is `manage`, also when an import does it (a mapping with new fields needs `manage` on top of `write`, `cannot_manage_fields` otherwise). Without the ability the answer is `403` with `"code": "token_ability_missing"`. A token never goes beyond its owner: the policies decide, for a token as for a session, so a viewer's `manage` token is refused like the viewer. Every route behind `auth:sanctum` in `routes/api.php` is classified, either `token:read|write|manage` (`App\Http\Middleware\RequireTokenAbility`) or session-only (`RefuseApiTokens`: the account, the administration and the tokens refuse any request that carries a token, even with the `Origin` of the front, with `"code": "session_required"`); a test fails for a route that is neither.
- **Limits.** `API_TOKEN_REQUESTS_PER_MINUTE` (120) requests a minute for each token (`App\Http\Middleware\PaceApiTokens`, right after the authentication: every request a token makes counts, the refused ones too), on top of the limits of the endpoints (uploads, exports, imports, creating workspaces and tokens...), which are a person's own and come after the refusals (a request refused for the token's ability or for being a session-only route does not use them up). `X-RateLimit-Limit` / `X-RateLimit-Remaining` describe the limit with the fewest requests left. Beyond a limit: `429` in JSON, `{"message": "…", "code": "too_many_requests"}`, with `Retry-After`. The web front has no token and is not counted by the token pace.

| Variable                        | Default | What it does                                              |
| ------------------------------- | ------- | --------------------------------------------------------- |
| `SANCTUM_TOKEN_PREFIX`          | `inv_`  | What every token starts with, so that a leaked one is easy to spot. |
| `API_TOKEN_REQUESTS_PER_MINUTE` | `120`   | Requests a token may make in a minute.                    |
| `MAX_API_TOKENS`                | `20`    | Live tokens one person may have.                          |

### The documentation

The reference is at **`/docs/api`** (drawn by the server from the specification: no script of its own, nothing loaded from another host) and the specification itself, OpenAPI 3.1, at **`GET /api/v1/openapi.json`** (public, `Cache-Control: public, max-age=3600`, its `servers` entry built from `APP_URL`). Both are public and limited like the other public pages.

The specification is **written by hand** in `resources/openapi/v1.yaml` (in English; the labels of the page are translated), read by `App\Docs\OpenApi` (`symfony/yaml`, the parsed file kept in the application cache under the hash of its content: editing it needs no invalidation) and checked against the application by the tests in `tests/Feature/Docs`. They cannot show that the document is complete (a field no scenario ever returns is not looked at), but within what they exercise a drift fails:

- every route under `api/` is named, classified (reachable with a token ability, or for the web session only) and, if a token can reach it, documented once with the same method, path and ability (`x-ability`); every documented operation is a route; the routes of the web front are not documented;
- every operation has a scenario in `ApiContractTest.php` (keyed by `operationId`, and a test fails if the keys differ from the specification's) that makes a real call with a token and holds both sides to the specification (`opis/json-schema`): the body and the query it sends fit the `requestBody` and the parameters of the operation, and the answer fits the schema given for its status, with a property the schema does not name counted as a mistake. A JSON answer with no schema, or a file whose `Content-Disposition` is not documented as sent, fails too; the errors of the API, their codes and the examples of the document are held to it as well.

**Whoever changes the API updates the specification in the same pull request**: a new route needs `token:<ability>` in `routes/api.php`, an operation in the YAML (`operationId`, `tags`, `summary`, `x-ability`, the parameters, the body, the answers with `x-codes` for the error codes they carry; an answer that lists codes is written in full, not as a `$ref`, which OpenAPI 3.1 allows no siblings next to), and a scenario in the contract test. A new error `code` is added to the `x-codes` of the answers that send it (a test lists the codes the code writes and fails for one the specification does not know).

## Templates and public pages

A template is a ready-made inventory: the fields of an inventory (types, options, colored choices), a description and a few example rows, written in French and English. They are the catalogue the gallery, the API and the "new inventory" dialog offer.

- **Catalogue.** One JSON file per template in `inventory-templates/<slug>.json` (the folder is `inventories.templates_path`), the file name being the slug in the URLs. A contribution is a pull request on one file; there is no table and nothing to synchronize. `App\Inventories\Templates\TemplateValidator` documents the format and judges a file the way a real creation of fields does: the options of each field go through the rules and the normalization of its type, names are unique per language, texts are plain (no HTML, no Markdown), and the example rows are validated by `ItemValues` against the fields (a choice is named by its `key`, numbers are decimal texts, files have no example). A file that is not valid is **left out and logged as a warning**, never an error page, and `ShippedTemplatesTest` fails with a message for each problem of each shipped file.
  - *Format.* The optional integer `format` (1 when absent) is the version of the format a file is written in: a file with a higher one needs a newer inventaire.cloud and is left out with a log that says so. `$schema` and keys that start with `x-` are allowed at the top level and ignored (an editor's schema, a contributor's notes). A file whose name starts with `_` or `.` is not a template (a draft, a hidden file) and is not even read.
  - *Cache.* Judging the files costs more than reading them, so the verdict (the accepted templates, as decoded arrays) is kept in the application cache for 24 hours, under a key that hashes the name and the content of every file, `TemplateValidator::VERSION`, `TemplateValidator::FORMAT` and the supported languages: editing, adding or removing a file needs no invalidation, and the left-out files are logged when a verdict is made, not each time it is read. **Bump `TemplateValidator::VERSION` whenever the validator would judge a file differently** (a rule, a limit, a message, the options of a field type): `TemplateValidatorGoldenTest` fails until you do. `inventaire:upgrade` forgets the entry. Each process then rebuilds the templates from the arrays once and keeps them in memory: a long-lived worker sees a change after it restarts. A cache store that fails is logged as a warning and the files are judged in memory instead: the page is still served.
- **API.** `GET /api/v1/templates` and `GET /api/v1/templates/{slug}` are public, in the language of the request and limited to `INVENTORIES_TEMPLATES_PER_MINUTE` (60) requests per minute (`429`), counted for each signed-in person on their own and for each network when nobody is signed in; the public pages below and `/sitemap.xml` share another one, `INVENTORIES_PUBLIC_PAGES_PER_MINUTE` (300); an unknown slug is a `404` with `"code": "template_not_found"`. `POST /api/v1/workspaces/{workspace}/inventories` takes an optional `template` (a slug; `422` on `template` when unknown): the inventory and **all** its fields are made in one transaction (retried as a whole on a deadlock, nothing is left behind when a field fails), with the field names and choices in the language of the request. A template with more fields than `max_fields` is a `409` `field_limit_reached`. The example rows are never inserted.
- **Pages.** `/templates` (the gallery, by category) and `/templates/{slug}` are drawn by the server. The language comes from the address alone: no prefix is the language of the instance (`APP_LOCALE`), `/en/templates` is English, the prefixed address of the language of the instance redirects (301, to an address built from `APP_URL`, never from the `Host` header) to the one without prefix, and the language cookie is neither read nor written there. Such a page varies on `Cookie` only (not on `Accept-Language`, which decides nothing there), and every answer of the application is `Cache-Control: private, no-cache` unless it sets its own. A template page in a supported language the template is not written in is served with the text of the fallback language but is `noindex`, with the fallback page as its canonical address. "Use this template" leads to `/app/templates/{slug}`, which sends the person (after the login page if needed) to `/app/w/{workspace}?template={slug}`, a workspace where they may add inventories. After the login page, `/app` takes the person back to the page they were going to only if it is an `/app/...` page of the instance (`APP_URL`); any other remembered address is forgotten.
- **Search engines.** `APP_INDEXABLE` (`false` by default; `1`, `true`, `on` and `yes` turn it on, anything else leaves it off) decides. Off: `/robots.txt` disallows everything, every page carries `noindex` and `/sitemap.xml` is a `404`. On: `/robots.txt` allows the public pages, keeps robots out of `/app/`, `/api/`, `/install` and `/login` and announces `/sitemap.xml` (the home page, the gallery and each template in every language, with `hreflang` alternates, and the API documentation at `/docs/api`); the public pages carry a title, a description, the canonical address, `hreflang` alternates, Open Graph tags and JSON-LD; the pages of the application itself stay `noindex`. Every answer that is not a public page asking to be indexed (the application, the API, the errors, the sitemap, and everything when indexing is off) also carries the header `X-Robots-Tag: noindex`, from the same decision as the `<meta name="robots">`. Every address in these tags and in the sitemap is built from `APP_URL`, never from the request, so set it to the public address. `robots.txt` is a route: no file of `public/` may stand in front of it.

## Installing the app (PWA)

The web app can be installed from a browser (Chrome, Edge, or "Add to Home Screen" on iOS): it then opens at `/app` in a window of its own, with the name of the instance (`APP_NAME`) and an icon. Browsers offer that only in a secure context: serve the instance over HTTPS (see "Reverse proxy and HTTPS").

- **Files.** `GET /manifest.webmanifest` (name, language, colors, icons), `GET /sw.js` (the service worker, scope `/`) and `GET /offline` are routes: public, the same for everybody, with no session, no cookie and no CSRF token, and served before the installation (the wizard is an application page too). The icons are static files in `public/icons/` and `public/favicon.ico`. No file named `sw.js` may exist in `public/`: a web server would serve it before the application. The worker source is `resources/js/sw/service-worker.js`, a plain script that Vite does not build; `app.js` registers it once the page has loaded and only in a production build (`npm run build`): `composer dev` and the tests never register it (`resources/js/lib/service-worker.js`). The pages of share links do not register it either.
- **What the worker does.** It only handles navigations (the loading of a page). The network always comes first, and only when it fails (not when the server answers an error status) the worker shows the `/offline` page instead of the browser's error page. It never stores a page, an API response or a file: those are private, on devices that may be shared, and the application has no offline reading or editing. The only thing in its cache is the offline page, in the language of the browser at the time of the installation. The scripts, styles, images and API calls are not intercepted, and neither are the links to files, whose answer is a download and not a page: the files of the API (`/api/...`) and the attachments and thumbnails of a share link (`/s/{token}/items/...`; the page `/s/{token}` itself is handled). Navigation preload is not used: the browser would ask the server for every navigation the worker does not answer (a download, a form) on top of the request of the worker. Because a failed request can also mean that the server is down, the offline page says that the instance could not be reached, not that the person is offline. If the browser evicted the offline page from the cache, the worker puts it back after the next page that loads, without delaying that page.
- **Updates.** `/sw.js` starts with a line that gives the worker its configuration, including a version: a hash of the worker source, of the source of the offline page, of the translation files (`lang/*.json`), of the colors of the page and of `APP_NAME`. A browser fetches `/sw.js` whenever the application is opened and installs a new worker as soon as one byte differs, which takes over at once. Each version keeps its offline page in its own cache, `inventaire-offline-<version>`, and deletes the `inventaire-*` caches of the other versions when it activates (caches with another prefix are never touched). So a release that changes none of these things leaves the installed workers alone, and one that changes any of them needs nothing from the administrator.
- **Removing the worker.** To get rid of it for good, remove the `registerServiceWorker()` call of `resources/js/app.js` and replace the content of `resources/js/sw/service-worker.js` with the script below, then deploy and keep it until your users' browsers have fetched it. Browsers do not agree on what a `/sw.js` that answers 404 does to a worker that is already installed, so do not count on deleting the file: to retire the worker, serve this self-unregistering script at `/sw.js` for a while. Do not make it reload the open pages: the pages would register it again.

```js
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (event) => {
    event.waitUntil(
        (async () => {
            const names = await caches.keys();
            await Promise.all(names.filter((name) => name.startsWith('inventaire-')).map((name) => caches.delete(name)));
            await self.registration.unregister();
        })(),
    );
});
```

## Administration

The administrators of the instance (`users.is_admin`) have an "Administration" entry in the account menu, which opens `/app/admin/users` and `/app/admin/settings`. Everything is behind the `admin` gate (`Gate::define('admin')` in `AppServiceProvider`), judged on the account as stored at every request: promoting or demoting somebody takes effect at once. The pages need a signed-in session like the rest of the space and answer `403` to anybody who is not an administrator; the API (`/api/v1/admin/*`) answers `401` to a visitor, `403` to a non-administrator (whether the account in the path exists or not: the id is looked up after the gate, so nobody can count the accounts) and, like the other session actions, `403` with `"code": "not_stateful"` to a caller that has no session. A request that carries an API token (`Authorization: Bearer`) is refused with `403` and `"code": "session_required"` (`App\Http\Middleware\RefuseApiTokens`), even when it sends the `Origin` of the application, which makes Sanctum start a session and fall back to the token: a token, whatever its abilities, must not do what a person does to other people's accounts.

| Endpoint                          | What it does                                                                                                      |
|-----------------------------------|-------------------------------------------------------------------------------------------------------------------|
| `GET /api/v1/admin/users`         | `q` (a word of a name or address, case ignored) and `page`: 25 accounts per page, newest first, with `id`, `name`, `email`, `locale`, `is_admin`, `is_self`, `workspaces_count`, `created_at`, in the `data` envelope with `meta` and `links`. |
| `POST /api/v1/admin/users`        | `email`, `name` (one line: no control character, the rule of the account page): creates the account (`201`). `409` `account_exists` when the address already has one, `429` beyond 60 accounts an hour per administrator (`ADMIN_USER_CREATION_PER_HOUR`). |
| `PATCH /api/v1/admin/users/{id}`  | `is_admin`: makes the account an administrator or takes that away. `409` `last_administrator` when it is the last, `403` `not_administrator` when the caller was demoted meanwhile. |
| `DELETE /api/v1/admin/users/{id}` | Deletes the account (`204`). `409` `self_deletion` for the caller's own account, `409` `last_administrator`, `403` `not_administrator` when the caller was demoted meanwhile. |
| `GET /api/v1/admin/settings`      | The settings: `{"data": {"registration_open": true, "invitation_sign_up": true, "share_links_enabled": true}}`.  |
| `PUT /api/v1/admin/settings`      | `registration_open`, `invitation_sign_up` and `share_links_enabled` (all optional, but at least one setting is required, `422` otherwise): changes the settings that are sent, leaves the others alone, and answers with all of them as they are now. |

Accounts are identified by their numeric `id` here, which administrators see for every account (anybody else only gets their own, from `GET /api/v1/me`); anything but digits in the path is a `404`. The rules live in `App\Admin\UserAdministration`, whoever asks:

- **Search** (`q`) looks in `name` and `email` with the query builder's `whereLike()` through `App\Database\CaseInsensitiveSearch`, which is the one place that decides how text is searched: `ILIKE` on PostgreSQL, `LIKE` on MySQL and MariaDB, no engine-specific SQL anywhere. `%` and `_` typed by the person are ordinary characters, and the term is lowercased (the email columns of MySQL and MariaDB have a binary collation, where `LIKE` tells capitals from small letters; addresses are stored in lowercase). What an engine does not fold stays unfolded: PostgreSQL in a database created with the `C` locale only folds ASCII letters, and MySQL and MariaDB ignore accents in names where PostgreSQL does not.
- **Creating an account** goes through `Accounts::register()` like signing up (the address in canonical form, the personal workspace in the same transaction, a deadlock retried by `DeadlockRetries`), in the instance's default language (`app.default_locale`, that is `APP_LOCALE`: not `app.locale`, which the `SetLocale` middleware replaces with the language of each request). The person is not signed in and no code is created: a welcome mail (`WelcomeMail`: plain text and simple HTML, in the default language, with the sign-in page at `APP_URL`/login, never an address built from the request) tells them to sign in with the code they will be emailed. It is sent after the response, like the code mails. The name is one line (`App\Rules\PersonName`, the same rule as on the account page: no control character, line breaks included), and an administrator can create 60 accounts an hour (`admin.user_creation_per_hour` in `config/admin.php`, `ADMIN_USER_CREATION_PER_HOUR`): each one sends a mail to an address they choose.
- **Administrators.** Promoting, demoting and deleting lock the administrators, the administrator who asks and the account in one statement, lowest id first (`Locks::administratorsAnd()`): the administrators are read first without a lock and everything is then locked **by primary key**, never with a filter on `is_admin`, which on MySQL and MariaDB would lock the whole table and the gap where new accounts are inserted, and make sign-ups and sign-ins wait for the end of a deletion. An account found to be an administrator among the locked rows is one until the commit (one promoted a moment before is not counted, which can only make a demotion refused for no reason, never wrongly allowed). Two administrators demoting each other at once are judged one after the other: the second one is no administrator any more when its turn comes, and is refused with `403` `not_administrator` (the administrator who asks is judged again under the locks, on every change). An administrator may step down when another one remains (`last_administrator` otherwise); the page offers no action on the administrator's own row.
- **Deleting** is `User::delete()`, the same path as the owner's own deletion (see [Deleting the account](#deleting-the-account)): the workspaces nobody else belongs to go with it, the others just lose a member. The caller's own account is refused (`self_deletion`: that takes the code mailed to its owner, from the account page), and so is the last administrator. Where the owner's deletion is refused for being the only owner of a workspace others belong to, an administrator's deletion **hands it over first**: the **editor** of the longest standing (the oldest membership, `workspace_user.id` being the order of joining) becomes its owner, or, when it has no editor, the member of the longest standing, whatever their role, and each shared workspace the account alone owns has its own successor. A workspace with another owner is left alone. The hand-over and the deletion are one transaction, under the locks of `App\Workspaces\Locks` in their global order (the sign-in code of the address, then the administrators, the administrator who asks, the account and the possible successors in one statement, then the workspaces, then the memberships): if the deletion is refused or fails, nobody's role has changed, and an account deleted by an administrator while one of the members deletes themselves leaves no workspace without an owner. Nobody is told of the change of owner (notifications come with member management, lot 9).
- **Log.** Each account created, made an administrator, stripped of that and deleted leaves one `info` line in the application log (`Administration: account deleted.`...) with the id of the administrator and the id of the account (`actor_id`, `target_id`) and nothing else: no address, no name. A request that changes nothing or is refused writes none. There is no audit table.

The users page lists the accounts with their badges, a search box, pagination, a creation form, a button that grants or removes administrator rights and a delete button that asks for a confirmation in the row; all of it through the API, with `adminUsers` (`resources/js/components/admin-users.js`).

### Closing registration

`registration_open` (the "Anybody can create an account" switch of the settings page, `PUT /api/v1/admin/settings`) is on until an administrator turns it off. It is stored in the `settings` table (a `key` and a JSON `value`) and read through `App\Settings\InstanceSettings`: typed getters, the default (open) when the row is absent, **closed** when the row is there but unusable (JSON that does not decode, or a value that is not a boolean, such as `"false"` or `0`: opening the instance on the strength of a value nobody understands is the wrong way to fail; one warning per request in the log, with the name of the setting and never its value), all rows read in one query the first time a request needs a setting and kept for that request only (a scoped service). Nothing is cached longer, so a change is seen by the very next request on any server or worker, at the price of one small query on the pages that need a setting.

Closed, only the addresses that already have an account sign in, and nothing reveals which they are:

- **Asking for a code** (`POST /api/v1/auth/code`) does the same work and gives the same answer for every address, headers included: a code is stored and the answer goes out. Whether to send the mail is decided afterwards, in the deferred callback, which is also where the account is looked up. An address with an account gets its code; any other address gets nothing in its mailbox, but **a code is stored for it all the same, one nobody receives**. Without it, typing a code back would tell them apart (an address with a pending code answers "incorrect code, n attempts left", an address without one answers "expired"), and the sign-in step would be the enumeration the request step avoids. For the same reason a mail that fails to send does not delete the code while registration is closed (it does when it is open, where every address is in the same case): an address whose mail failed would otherwise answer "expired" and one that has no account "incorrect", for whoever probes while the mail server is down. An undelivered code does no harm: nobody knows it, and it lapses.
- **Typing a code back** (`POST /api/v1/auth/verify`) judges every address the same way (attempts counted, the lock after too many wrong codes), but for an address without an account no code is ever the right one: even a code issued before registration closed is refused as a wrong code, which costs an attempt, and the page does not ask for a name, since that would say the code was right. Reopening registration lets the codes that still have attempts left work again.
- **Closed means "on invitation".** While `invitation_sign_up` (the second switch of the settings page; on by default) is on, an address without an account that a workspace invited is treated as an address with one for the code: `App\Workspaces\Invitations::hasTicketFor()` finds a waiting, unexpired invitation to the address **whose sender still has an account** (`invited_by_id` is null once that account was deleted, and such an invitation is nobody's ticket; it can still be accepted by a person who has an account). Turned off, invitations open nothing and accounts come from the administrators alone; it has no effect while registration is open. Like `registration_open`, an unusable stored value counts as *off*. The look for an invitation is made for every address, whatever the setting, and answers stay identical; what differs happens after the answer (an address with an account is not looked up for an invitation, the mail goes to some addresses only), as for the accounts above, so the same note on the web server applies: a development server holds the connection until that work is done.
- `/login` says to everybody alike that sign-ups are closed ("only existing accounts can sign in", with "and invited addresses" while invitations are on), and the administrators keep creating accounts from the users page.

### Mails are sent after the response

The mails that carry a code (sign-in, account deletion) and the welcome mail are sent once the response has gone, with Laravel's `defer()` wrapped by `App\Mail\AfterResponse`, **never through the queue**: a queued job is stored in clear in the `jobs` table (and in `failed_jobs` when it fails), and these mails carry codes that the application only ever keeps as hashes. The visitor does not wait for the mail server and the answer does not depend on it. What follows from it:

- The deferred work runs only for a successful response (below 400), when the process terminates the request. A crash or a kill in between loses the mail: the person asks for another code.
- A send that fails is not visible to the visitor. The code that was issued is deleted (only that one: a newer code the person asked for in the meantime stays; the sign-in code of an address is kept while registration is closed, see above) and the failure is logged at `error` level (`Could not send a sign-in code: <exception>: <message>`), never with the code, and with every email address in the message replaced by `[address]` (a mail server's answer often names the recipient). The person simply asks again.
- **The web server decides whether "after the response" is true.** FrankenPHP (the Docker image, in its default mode), PHP-FPM and LiteSpeed finish the response before the work runs (Symfony's `Response::send()` calls `fastcgi_finish_request()` or its LiteSpeed twin). PHP's built-in server and so `php artisan serve` (and `composer dev`) cannot: the connection stays open until the script ends, so the visitor does wait for the mail, as they would have before. They are development servers, but note that, with registration closed, the time the connection takes to close then shows whether a mail was sent, that is whether the address has an account. In production the answer is complete before the lookup and the sending begin. In tests, the deferred work runs as the request terminates, inside the call; `holdDeferred()` in `tests/Pest.php` holds it back to look at what happens between the answer and the mail.
- The install wizard's mail check (`SetupCodeMail`) is not concerned: it exists to tell the person at once whether mail works, so it is sent and its failure shown on the spot.

## Your account: sessions, data and deletion

`/app/account` ("My account") holds the profile (name, language), the security of the sessions, the download of the data, and the deletion of the account.

### Signing out everywhere

`POST /api/v1/me/sign-out-everywhere` (the web front only) ends the sessions of every device but the current one and revokes the account's API tokens (a lost device may hold one; they are not tied to a session). It renews the account's remember token and signs the current device in again with a fresh session, a cookie for the new token and the new fingerprint (the framework stores it in the session as the device signs in, before any other request).

How it works: the framework ties a session and a "remember me" cookie to a "password hash" of the account. Accounts have no password, so `User::getAuthPassword()` derives that fingerprint from the remember token (an HMAC with `APP_KEY`, empty for an account without a token). The cookie carries the token itself, so a copied cookie with an old token no longer finds the account; a session stores the fingerprint when it is opened, and `AuthenticateSession` signs it out as soon as it differs. That check runs on the pages of the signed-in space only (the `auth` routes of `routes/web.php`: `/app/*`), with `App\Http\Middleware\AuthenticateSession` (the framework's, which waits for the installation to be over so that the install wizard never looks anybody up), and on the API with `App\Http\Middleware\AuthenticateApiSession` (Sanctum's own middleware for the requests of the web front, replaced in `config/sanctum.php`). The public pages never look the visitor up for it: a visitor with a revoked session who opens the home page simply sees it, and is signed out when they enter `/app`. Both refuse a signed-in session that carries no fingerprint (`App\Auth\SessionFingerprint`) instead of giving it the current one as the framework does, which would let a session that predates the fingerprints outlive any sign-out everywhere; a request signed in by a valid "remember me" cookie is not concerned, because every sign-in leaves its session with the fingerprint, on any route: the guard fires `Login` for a sign-in by cookie as well, and `App\Auth\StoreSessionFingerprint` listens to it, so a visitor whose session expired and whose cookie signs them in on a public page (the home page, the login page) keeps it for their next click into `/app`, while a cookie from before a sign-out everywhere (its token was renewed) signs nobody in and gets nothing. Signing out of one device keeps the token, so the others stay signed in. Every account gets a token when it is created, and the migration `give_every_user_a_remember_token` gives one to those that have none.

Because the fingerprint stands where the framework expects a password hash, a few framework helpers misbehave on this application and must not be used: `logout()` (renews the shared token, so it signs the account out of every device), `logoutOtherDevices()` and the `password.confirm` middleware. Sign out of this device with `logoutCurrentDevice()`. `tests/Unit/AuthenticationGuardrailsTest.php` fails if `app/`, `routes/` or `bootstrap/` use them.

When updating an instance that did not have this: a session opened before has no fingerprint, and is refused (whatever keeps the sessions: database, files, the cache or Redis), so **everybody signs in again once**, with a code, at the update. A "remember me" cookie issued before carries the previous constant, empty fingerprint and is refused as well.

### Your data (GDPR)

`GET /api/v1/me/export` (throttled: `account_export` in `config/auth.php`) downloads `inventaire-export-YYYY-MM-DD.json`: the profile (with its `ulid`, the identifier the other members of a workspace know the account by), the workspaces with the role in each, the sessions the account has in the database (`sessions`: `ip_address`, `user_agent`, `last_activity`; empty when sessions are kept anywhere else) and the metadata of its API tokens (`tokens`: `name`, `abilities`, `last_used_at`, `created_at`). The document is versioned (`format`, `version`). Each workspace carries its `inventories`: for every one its `id`, `name`, `description`, dates, `fields` (`id`, `name`, `type`, `options`, `required`, `position`) and `items_count`, the **number** of its items; and, for each workspace, `revisions_written` (the lines of the history of items the account wrote) and `files_uploaded` (`count` and `bytes` of the files it uploaded). **The items themselves are not in the file**: an inventory can hold thousands of them, too many for a document built in memory and sent in one answer. Their content comes with the export of the inventories (lot 6), streamed one inventory at a time. `share_links` lists the share links the account made from the workspaces it still owns (inventory, label, whether the files are shown, dates), never the address. Nothing secret is in it (no session id, no token, no hash), and nothing about other people.

### Deleting the account

Deleting cannot be undone, so it takes a code mailed to the address of the account, in two steps (both session actions, for the web front only):

1. `POST /api/v1/me/deletion-code` mails a 6-digit code, in the language of the account (plain text and simple HTML, like the sign-in code's mail), after the response like the sign-in codes. It is a code of its own: it lives in the `account_deletion_codes` table (one row per user, a keyed hash derived from `APP_KEY`, the purpose and the user, valid 10 minutes for 5 wrong guesses), never replaces or spends a sign-in code, and cannot be used for one. Sending is throttled per user (3 per 10 minutes, 6 per hour).
2. `DELETE /api/v1/me` with `{ "code": "123456" }`, throttled to 5 per minute. A code that is not accepted is a `422` with `"code"` set to `deletion_code_wrong`, `deletion_code_expired` (never asked, replaced or expired) or `deletion_code_exhausted`.

The limits are in `account_deletion` in `config/auth.php`. There is one way to delete an account, whoever asks (this page, an administrator from [Administration](#administration), `tinker`): `User::delete()`. It runs in one transaction (if anything fails, nothing is deleted; a deadlock is retried) and the model's `deleting` event calls `AccountDeletion::release()`, which judges the rules and removes what goes with the account under the locks described in [Workspaces](#workspaces) (the sign-in code of the address, then the administrators and the account in id order, then its workspaces), so that two administrators deleting themselves at once, or two co-owners, are judged one after the other, and a deletion and a sign-in of the same address cannot deadlock. Deleting an account that is already gone (a stale copy of it, or somebody else deleted it first) raises a `ModelNotFoundException` instead of reporting a deletion that deleted nothing; the API answers `404` with `"code": "account_not_found"` and ends the session of that device, as after a deletion. Deleting rows with a query raises no model event and is not a way to delete an account. It removes:

- the workspaces that nobody else belongs to, with everything in them, each one through its own `Workspace::delete()` so that its model events fire (what lot 4 stores for a workspace, files on disk or S3, is purged there);
- the account's place in the workspaces shared with other people (it just leaves them);
- its rows in the `sessions` table (when sessions are kept in the database), the sign-in code waiting for its address, its deletion code and its API tokens, then the user.

The device is signed out at the end. Two things stop a deletion, with a `409` and a `code` that the card on the account page explains (it asks as soon as the code is requested, and again when it is confirmed; the code is kept, so nothing has to be asked again once the obstacle is gone):

- `sole_owner_of_shared_workspaces`: the account is the only owner of workspaces that other people belong to. The body lists them (`workspaces`: `id` and `name`). Ownership has to be handed over first; the screens to do it come with member management (lot 9). (An administrator who deletes the account from the administration hands the workspaces over to their longest-standing member by itself.)
- `last_administrator`: the account is the last administrator of the instance. Make somebody else one first with `php artisan inventaire:make-admin`.

## Upgrading an instance

After every update of the code, bring the instance up to date:

```bash
git pull
composer install --no-dev --optimize-autoloader
npm ci && npm run build
php artisan inventaire:upgrade --optimize
```

An instance installed before sign-in existed has no administrator and the upgrade does not create one (the installer's hooks only run during the installation): create one with `php artisan inventaire:make-admin you@example.com --name="Your Name"`. The same upgrade removes the `password` column and the `password_reset_tokens` table, which accounts no longer use.

The upgrade that brings workspaces gives every existing account a personal workspace and a remember token (idempotent migrations). It also leaves the sessions opened before without a fingerprint, which are refused, and a "remember me" cookie issued before is refused as well: **everybody signs in again once**, with a code (see [Signing out everywhere](#signing-out-everywhere)).

The upgrade that follows brings dates stored in UTC. Until then they were stored in the timezone of the instance (`APP_TIMEZONE`); the migration converts them from that timezone to UTC, so keep `APP_TIMEZONE` as it was until the upgrade has run. It also deletes the sign-in and account deletion codes that are pending: whoever was waiting for one asks for another. `APP_TIMEZONE` is from then on the display timezone only (rolling the migration back converts the dates back).

`inventaire:upgrade` reloads the configuration (so an edited `.env` is used), applies the pending migrations under a file lock (a second upgrade running at the same time waits for it, up to 10 minutes) and clears the route, view and event caches. With `--optimize` it rebuilds them afterwards; it can be run as often as you like, and with Docker the update is automatic (see below).

## Self-hosting with Docker

The image bundles PHP, the web server (FrankenPHP) and the built front end: you need Docker with Compose, not PHP or Node. `docker/compose.yaml` is a ready-to-use example with the application, two queue workers (`worker` for the short jobs, `export-worker` for the exports and the imports), a scheduler and PostgreSQL.

```bash
cd docker
cp .env.example .env        # set DB_PASSWORD at least
docker compose up -d --build
```

The application listens on <http://localhost:8080> (`APP_PORT` in `.env` changes the port). Everything below is run from the `docker/` folder.

### Two ways to configure it

- **Wizard.** Set `DB_PASSWORD` only. Open the application: it redirects to the install wizard, which asks for the rest. Its one-time setup token is printed by `docker compose exec app php artisan inventaire:install-token`. The database settings come from the compose file, so the wizard shows them read-only.
- **Environment.** Put the whole configuration in `.env` (the full list is in `docker/.env.example`: URL, language, display timezone, SMTP, file storage, the first administrator `ADMIN_NAME` and `ADMIN_EMAIL`...). Every variable set there reaches the container as a real environment variable and shows read-only in the wizard ("set by the environment"). When nothing is left to ask, the instance installs itself the first time the `app` container starts, with the same live checks as the wizard (database, SMTP, storage). If one fails the container stops with the reason (`docker compose logs app`) and Compose retries until you fix it.

### What is kept where

The `storage` volume is `/app/storage`: it holds the configuration the installer generates (`.env`, with `APP_KEY` and the secrets entered in the wizard), the uploaded files, the installer state (including the "installed" marker) and the logs. **Back it up together with the database, and keep it private**: whoever reads it can read your secrets, and an instance whose database survives but whose `APP_KEY` is lost cannot decrypt what it stored. Do not delete the volume unless you mean to erase the instance. If you replace it with a host folder, make it writable by user ID 1000, the unprivileged user every process of the container runs as.

`APP_ENVIRONMENT_FILE` (default `/app/storage/.env`) tells Laravel and the installer which file holds that configuration. It must be an absolute path; Laravel prefers a file named like it followed by `.` and `APP_ENV` (`.env.production`) when one exists in the same folder, so keep none there.

`APP_ENV`, `APP_DEBUG` and `LOG_CHANNEL` are environment variables of the image (production mode, errors on stderr), not entries of that file: a real environment variable always wins over it. To change them, set them in `docker/.env`, not in `/app/storage/.env`.

### Updating

```bash
git pull
docker compose up -d --build
```

When the `app` container starts on an installed instance it runs `inventaire:upgrade --optimize` before serving: the migrations are applied and the caches rebuilt. If the update fails (a migration, for instance) the container stops with a non-zero status instead of serving a half-updated instance; read `docker compose logs app`. Compose restarts the workers and the scheduler whenever it recreates or restarts `app` (`restart: true` in their `depends_on`), so they run the new code once the application is healthy. Back up before updating.

To run the update by hand, without recreating the containers:

```bash
docker compose exec app php artisan inventaire:upgrade --optimize
docker compose restart worker export-worker scheduler
```

### Another database server

`docker/compose.yaml` bundles PostgreSQL. To use a server you already have (PostgreSQL, MySQL or MariaDB), delete the `db` service, the `depends_on` entry of `app` that waits for it, and the `DB_*` lines of the shared environment. The wizard's database step is then editable; or put `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD` in `docker/.env` to install without the wizard. Commented examples of bundled MySQL and MariaDB services are at the end of the file.

### Reverse proxy and HTTPS

The container speaks plain HTTP on port 8080. Terminate TLS in a reverse proxy in front of it, set `APP_URL` to the public `https://` address, and set `TRUSTED_PROXIES` in `.env` to the proxy's address or CIDR range (see "Behind a reverse proxy"): otherwise every visitor looks like the proxy and the setup token throttle counts them together. Opening the container directly over plain `http` (for instance `http://localhost:8080`) with an `https://` `APP_URL` loses the session: see `SESSION_SECURE_COOKIE` under "Behind a reverse proxy". Keep the proxy from overriding the `Referrer-Policy: same-origin` header the application sends (see "Behind a reverse proxy").

HTTPS is also what makes the application installable and the camera usable: browsers only allow service workers (see "Installing the app (PWA)") and `getUserMedia` (the barcode scan) in a secure context, which means HTTPS, or `localhost` in development. Over plain HTTP on any other address the application works, but it cannot be installed, and scanning falls back to taking a photo.

## Testing on PostgreSQL, MySQL and MariaDB

The application has to behave the same on all three engines, and SQLite is deliberately not supported. The database tests (`RefreshDatabase`) run the real migrations, so running the suite on each engine catches engine-specific SQL early. The services must be running (`docker compose -f compose.dev.yaml up -d --wait`):

```bash
composer test         # PostgreSQL, MySQL, then MariaDB; stops at the first failure
composer test:pgsql   # PostgreSQL only
composer test:mysql   # MySQL only
composer test:mariadb # MariaDB only
```

`phpunit.xml` points at the PostgreSQL service and its dedicated `inventaire_test` schema, so `composer test:pgsql` (and a plain `php artisan test`) need no extra setup; `composer test:mysql` and `composer test:mariadb` override `DB_*` to use their own service and its `inventaire_test` schema.

The tests never touch the real `.env`, installer state, cached configuration or storage: `phpunit.xml` points `INSTALLER_STATE_PATH`, `INSTALLER_ENV_FILE`, `APP_CONFIG_CACHE`, `APP_ROUTES_CACHE`, `APP_EVENTS_CACHE`, `VIEW_COMPILED_PATH` and `CACHE_FILE_PATH` at a throw-away folder below `storage/framework/testing/`, emptied around every test (`tests/Support/InstallerSandbox.php`). Every test boots in the "installed" state, so tests that predate the installer are unaffected; a test that needs a fresh instance calls `$this->bootInstaller(installed: false)`. Run the suite sequentially: the sandbox folder is shared. (`composer test` itself starts with `php artisan config:clear`, which does clear the real cached configuration.)

Switching `actingAs()` from one user to another inside a test needs `$this->flushSession()` in between: the session fingerprint of the first user is still in the store.

Safety net: `tests/TestCase.php` refuses to boot (before any migration) unless the configured database name ends with `_test`. A stale cached config (`php artisan config:clear` fixes it) or a `DB_DATABASE` exported in your shell can therefore never wipe the development database.

## Conventions

- **One HTTP helper.** Scripts never call `fetch` directly: they use `http` from `resources/js/lib/http.js` (see below).
- **No display text in JavaScript.** Strings that scripts need are translated on the server and embedded by `<x-client-messages />`; scripts read them with `t('key')`.
- **Alpine, CSP build.** The app uses `@alpinejs/csp`, so a strict Content-Security-Policy without `'unsafe-eval'` can be enforced (the header itself arrives in a later lot). In practice:
  - every component is registered in `resources/js/app.js` with `Alpine.data('name', factory)` and referenced by name in the markup (`x-data="toasts"`), never with an inline object;
  - expressions in templates stay simple: property access, method calls with arguments, comparisons, `!`, `&&`/`||`, ternaries and string `+`. Arrow functions, template literals, `;` statements and Blade values interpolated inside an expression are not allowed: put that logic in a component method;
  - a component gets its values from `data-*` attributes (`data-url` on the root, `data-locale` on an item), read through `$root` or `event.currentTarget`, and translated texts are rendered by Blade as plain attributes;
  - `tests/js/templates/alpine-csp.test.js` scans every Blade template for forbidden syntax and mounts the toast markup with the real CSP build; `tests/js/templates/pages.test.js` does the same for the workspace switcher, the workspaces page, the account page and the administration's users and settings pages, and drives them like a person would. Alpine applies what a click changed within a frame or two: wait with `requestAnimationFrame`, not only with `nextTick`.
- **Icons.** Use `<x-tabler-*>` components and do not pass a `class` attribute: the SVG files already have one, which would render the attribute twice. Size and space icons from a parent element.
- **Documentation.** Every class and public method carries a PHPDoc/JSDoc block that explains the why, not only the what.
- **Language.** Code, identifiers, comments and commit messages are in English.

## HTTP helper

`http.get/post/put/patch/delete` is the contract every action relies on. It sends JSON with `Accept`, `Accept-Language`, `X-Requested-With` and the CSRF token (`X-XSRF-TOKEN` from the `XSRF-TOKEN` cookie, falling back to the `csrf-token` meta tag, so rotation after login or logout is followed). It resolves the parsed JSON, `null` for `204`, or a `Blob`/text with `{ responseType: 'blob' | 'text' }`; a `FormData` body is sent as is. `{ timeout }` (default 30 s, covering the body too) and `{ signal }` can be combined.

Failures throw an `HttpError` (`status`, `message`, `errors`, `code` from `body.code`, `retryAfter`, `kind`, `reported`). Raw response messages are never shown, except the server-translated validation messages of a `422`; everything else is looked up by key in the strings embedded by `<x-client-messages />`.

| Situation              | Central handling (skip all with `{ silent: true }`)                                              |
|------------------------|--------------------------------------------------------------------------------------------------|
| `401`                  | Toast, then redirect to the `login-url` meta tag (every page has it: the `login` route exists), else reload |
| `403`, `404`           | Toast                                                                                            |
| `419`                  | Refresh the token (`csrf-refresh-url` meta tag) and replay once; only a second failure toasts and reloads |
| `422`, other `4xx`     | Nothing: the caller handles it (`errors`, `code`)                                                |
| `429`                  | Toast; `retryAfter` holds the `Retry-After` delay in seconds                                     |
| `5xx`                  | Toast                                                                                            |
| Network, timeout       | Toast (`HttpError.status === 0`, `kind` is `network` or `timeout`)                               |
| `2xx` that is not JSON | Toast and `HttpError` with `kind === 'unexpected_response'`                                      |

A page that is open to visitors (the sign-in page, the user menu's sign-out) must pass `{ silent: true }` and show the failures itself: the central handling would answer a `401` or a `403` by redirecting to the very page the visitor is on.

A request cancelled through the caller's `signal` rejects with the raw `AbortError` and no toast. `delete` takes no body by convention; the few deletions that ask for a confirmation pass it as `http.delete(url, { data: { code } })`. `t('key', { name: value })` fills the `:name` placeholders of a message.

## Translations

French is the default language and English the fallback. Interface strings are written in English in the code with `__()` and translated in `lang/fr.json`; framework messages (validation, authentication, pagination, passwords) come from [laravel-lang](https://laravel-lang.com).

The language of a request is chosen by `App\Services\LocaleResolver`, trying in order: the one-year `locale` cookie written by `PUT /locale` (and by signing in, from the account's `users.locale`), the best `Accept-Language` match, then the default. The `SetLocale` middleware is global and runs first, so 404 pages, expired-session errors and the future API are localized too, and responses carry `Content-Language` and `Vary: Accept-Language, Cookie`. The `locale` cookie is excluded from encryption because its value is validated against the supported list on every read. The account's language is not a source of its own because the resolver runs before the session and the authentication, which a 404 page or the install wizard should not have to start: see [Accounts and sign-in](#accounts-and-sign-in).

To add a language, for example Spanish:

1. Add `es` to `locale_names` in `config/app.php` (its keys are the supported locales).
2. Run `php artisan lang:add es` for the framework messages and `lang/es.json`, then translate the project strings in it.

The language switcher and the `PUT /locale` endpoint pick the new locale up from the configuration.
